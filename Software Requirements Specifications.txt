# Restaurant POS SaaS - Master Development Instructions

## Project Objective

We are building a **commercial-grade cloud Restaurant Management & POS Software**.

This is **NOT** a college project or a simple POS.

The software must be designed from Day 1 as a scalable SaaS platform that can eventually support thousands of restaurants.

The first deployment will be in a family restaurant for production testing.

After successful validation, the same software will be commercialized for restaurants, cafés, bars, bakeries, pizzerias, food trucks, hotels and restaurant chains.

Everything must therefore be designed with long-term scalability, maintainability and extensibility in mind.

---

# Important Development Philosophy

This project has a GitHub repository selected as a **reference implementation**.

Repository: [https://github.com/ahmedali5530/restaurant-pos]

This repository **is NOT our codebase**.

Do NOT clone it and continue development.

Do NOT tightly couple our software to it.

Instead, use it as a professional reference library.

Study its:

* UI/UX
* User workflows
* Business logic
* POS interactions
* Modules
* Components
* Functions
* Calculations
* Printing workflows
* Order flow
* Inventory flow
* Reports
* Screen layouts

Reuse ideas whenever they improve productivity.

If a module in the repository is well designed, recreate similar functionality inside our own architecture.

The repository exists to save development time, not to define our architecture.

Our software must remain completely independent.

Always prefer:

* clean architecture
* modular code
* reusable components

# SaaS First Design

This software MUST be SaaS ready from Day One.

Do NOT build a single restaurant application first.

Every module must support multiple restaurants.

Every database entity must support tenant isolation.

Examples:

Restaurant

Users

Products

Orders

Tables

Inventory

Reports

Customers

Settings

Everything must be tenant-aware.

No assumptions should ever exist that there is only one restaurant.

---

# Offline First

Offline mode is mandatory.

Restaurant should continue operating even without internet.

Requirements:

* Local cache

* Offline billing
* Automatic synchronization
* Conflict resolution

# Non-Negotiable Rules

* Do NOT build a temporary solution that will need rewriting later.
* Do NOT tightly couple modules.
* Do NOT hardcode business rules.
* Do NOT assume only one restaurant.
* Do NOT blindly copy the reference repository.
* Use the repository only as inspiration and productivity acceleration.
* Always prioritize clean architecture over quick implementation.
* Every design decision should consider future SaaS commercialization.
* If there is a choice between a quick fix and a scalable solution, choose the scalable solution.

The objective is not just to create a POS. The objective is to build a modern, commercial-grade Restaurant Management SaaS platform capable of competing with established products in the Spanish market while remaining maintainable, extensible, and production-ready for years to come.
